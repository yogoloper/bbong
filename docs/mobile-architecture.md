# BBONG 모바일 구조 설계

> 작성 2026-08-12. 웹 검증을 마치고 Google Play / App Store 출시로 넘어가는 시점의 구조 설계입니다.
> 남은 일정과 블로커는 `mobile-roadmap.md`, Phase 1~5 시점의 구조는 `architecture.md`,
> 리스크 대장은 `considerations.md`를 봅니다. 이 문서는 그 위에 "모바일에서 무엇을 어떻게 바꾸는가"만 다룹니다.

## 0. 전제

이 문서를 쓰면서 세운 판단 기준이 셋 있습니다.

첫째, 게임은 이미 동작합니다. 룰 엔진, 서버 권위 진행, 판돈 정산, 재접속까지 다 돌아가고 100인 부하 테스트도
통과했습니다. 그러니 여기서 다루는 것은 전부 "앱으로서 성립하게 만드는" 주변부이고, 게임 코어를 건드리는
제안은 하지 않습니다.

둘째, 유저가 아직 없습니다. 동시 접속 수치도, 실제 이탈 패턴도, 규제 분류 결과도 모릅니다. 이 상태에서
수평 확장이나 상태 외부화 같은 큰 구조 변경을 미리 넣으면 검증되지 않은 복잡도만 남습니다. 그래서
"지금 안 하면 출시가 막히는 것"과 "나중에 해도 되는 것"을 구분하고, 후자는 §10에 명시적으로 모아
두었습니다.

셋째, GRAC 웹보드 분류 결과가 언제 나올지 모릅니다(R1). 판돈을 넣은 채 출시할 수 있을지가 이 결과에
달려 있는데, 결과를 기다리다 출시를 미루는 것도, 넣고 나서 다시 빼는 것도 나쁩니다. 그래서 §8에서
판돈을 앱 재배포 없이 서버 쪽에서 끄고 켤 수 있는 구조를 제안합니다. 이건 지금 넣어야 나중에 쓸 수
있는 종류의 것이라 우선순위가 높습니다.

## 1. 클라이언트 구조 — 앱 전역 계층

### 지금 어떻게 돼 있나

화면 하나당 MonoBehaviour Bootstrap 하나이고, 전환은 `UiKit.GoTo<T>`가 담당합니다
(`UiKit.cs:291-300`). 새 GameObject를 만들고 현재 캔버스와 현재 컴포넌트를 파괴하는 세 줄짜리 함수입니다.
씬은 사실상 하나뿐입니다.

여기서 짚어둘 게 있는데, 앱 전역 상태를 들고 있는 계층이 "없는" 게 아니라 이미 두 개 있습니다.
하나는 `Session` static 클래스(`Session.cs`)로 토큰·유저 id·닉네임·잔액을 들고 있고, 다른 하나는
`WsClient`로 `DontDestroyOnLoad` 싱글턴 MonoBehaviour입니다(`WsClient.cs:54-68`). 화면이 파괴돼도
소켓과 세션은 살아남습니다. 그래서 "전역 계층이 필요한가"가 아니라 "그 계층이 무엇을 더 맡아야
하는가"가 진짜 질문입니다.

### 무엇이 부족한가

모바일에서 필요한 네 가지를 지금 구조가 받을 자리가 없습니다.

앱 생명주기가 첫 번째입니다. `OnApplicationPause`와 `OnApplicationFocus`는 MonoBehaviour 콜백인데,
`Session`은 순수 static이라 이걸 못 받습니다. `WsClient`는 MonoBehaviour이지만 소켓 펌프 역할만
하고 있고, 백그라운드 진입 시 무엇을 할지 정하는 건 소켓 계층의 일이 아닙니다. 실제로 지금 클라
코드 전체에 `OnApplicationPause`/`OnApplicationFocus`가 한 건도 없습니다.

두 번째는 화면과 무관한 비동기 작업입니다. `UiKit.GoTo`가 현재 컴포넌트의 GameObject를 파괴하므로
그 위에서 돌던 코루틴도 같이 죽습니다. 토큰 갱신이나 자동 재연결처럼 화면 전환과 무관하게
계속돼야 하는 작업을 걸 곳이 없습니다.

세 번째는 안드로이드 뒤로가기입니다. `Escape` 키를 처리하는 코드가 없어 Unity 기본 동작인 즉시
종료가 그대로 나옵니다. 화면마다 뒤로 동작이 다르므로 전역에서 키를 받아 현재 화면으로 넘겨줄
주체가 필요합니다.

네 번째는 딥링크와 푸시입니다. 둘 다 앱이 켜지는 순간이나 백그라운드에서 도착하는데, 그때 살아
있는 상주 객체가 받아야 합니다.

### 권고: AppHost 하나만 추가합니다

씬 구조도, 화면 전환 방식도, 코드 생성 UI도 바꾸지 않습니다. `DontDestroyOnLoad` 싱글턴
MonoBehaviour 하나(`AppHost`)를 추가하고 딱 다섯 가지만 맡깁니다. `WsClient`가 이미 정확히 이 패턴
이므로 새로운 개념이 들어오는 게 아닙니다.

1. **부팅 결정.** 저장된 자격으로 로그인을 복원하고 `/me`로 검증한 뒤, 성공이면 메인 로비를, 실패면
   로그인 화면을 첫 화면으로 띄웁니다. 지금은 `AuthBootstrap`이 씬에 직접 배치된 진입점인데
   (`AuthBootstrap.cs:16-20`), 이 판단을 AppHost로 옮깁니다.
2. **생명주기 중계.** `OnApplicationPause`/`OnApplicationFocus`를 받아 현재 화면과 `WsClient`에 알립니다.
3. **뒤로가기 중계.** Input System(`UiKit.cs:28`에서 `InputSystemUIInputModule` 사용)의 escape 키를
   `Update`에서 감지해 현재 화면의 뒤로 동작을 호출합니다.
4. **장수명 코루틴 소유.** 토큰 갱신, 자동 재연결 백오프처럼 화면과 무관한 작업을 여기서 돌립니다.
5. **딥링크 수신.** `Application.deepLinkActivated`를 받아 초대코드를 보관해 두었다가 로비에 도달했을 때
   소비합니다.

### 백스택은 자료구조 없이 갑니다

화면 스택을 제대로 만들려면 각 화면의 상태(예: `FriendRoomBootstrap._room`)까지 복원해야 하는데,
`GoTo<T>`는 타입만 알고 상태를 모릅니다. 여기에 직렬화 가능한 화면 상태 모델을 도입하는 건 얻는
것에 비해 큽니다.

대신 이미 있는 것을 씁니다. 화면마다 뒤로가기 버튼이 정확히 하나씩 있고, 그 버튼의 콜백이 곧
"뒤로 갈 때 할 일"입니다(`LobbyBootstrap.cs:117`, `FriendRoomBootstrap.cs:68/87/154`,
`ShopBootstrap.cs:33`, `MatchSetupBootstrap.cs:87`, `ProfileBootstrap.cs:44`). `UiKit.BackButton`이
호출될 때 그 콜백을 AppHost의 "현재 뒤로 동작" 슬롯에도 등록하면, 스택 없이 슬롯 하나로 끝납니다.
`UiKit.BackButton` 본체 한 곳만 고치면 되므로 화면 코드는 손대지 않습니다.

예외가 둘 있습니다. 게임 테이블에는 뒤로가기 버튼이 없고 나가기 확인 모달이 따로 있으므로
(`NetGameTableBootstrap.cs:54-55`의 `ExitConfirmText`/`ExitConfirmed`), 뒤로가기 키는 이 모달을
띄우는 데 씁니다. 메인 로비는 뒤로 갈 곳이 없으므로 "한 번 더 누르면 종료"로 처리합니다.

### 대안으로 검토했다가 접은 것

`Session`을 MonoBehaviour로 승격시켜 AppHost 역할을 겸하게 하는 안이 있었습니다. 객체를 하나
안 늘려도 되지만, `Session`의 static 필드가 `ServerApi`, `UiKit.TopBar`, `FriendRoomBootstrap` 등
전 코드에 흩어져 참조되고 있어 호출부가 전부 흔들립니다. `Session`은 데이터 홀더로 그대로 두고
AppHost가 그것을 저장·복원하는 쪽이 변경 면적이 훨씬 작습니다.

## 2. 인증과 세션

### 지금 어떻게 돼 있나

| 항목 | 현재 상태 | 근거 |
|---|---|---|
| 토큰 보관 | `static string Token` (프로세스 종료 시 소멸) | `Session.cs:6` |
| 액세스 토큰 수명 | 60분, ClockSkew 0 | `JwtSettings.cs:16`, `:29` |
| 리프레시 | 없음 (`ITokenIssuer`에 `IssueAccessToken`만) | `ITokenIssuer.cs:8` |
| 게스트 로그인 | 호출할 때마다 새 Guid 계정 + 10,000P 지급 | `Program.cs:159`, `AccountService.cs:26-32` |
| 소셜 로그인 API | `/auth/social`, `/auth/link` 구현 완료 | `Program.cs:171`, `:191` |
| 소셜 검증기 | 미구현 (운영에선 무조건 예외) | `NotConfiguredSocialVerifier.cs` |
| 클라 소셜 버튼 | `interactable = false`, "준비중" | `AuthBootstrap.cs:46-50` |

정리하면 서버 쪽 소셜 흐름은 다 있고 provider 토큰 검증기만 비어 있습니다. `LinkSocialAsync`는
게스트 계정의 id와 잔액을 유지한 채 provider/subject만 채우고(`AccountService.cs:57-73`,
`UserAccount.cs:44-53`), 이미 다른 계정에 연동된 소셜이면 예외를 던집니다. 클라만 붙이면 됩니다.

### 토큰 저장소

`PlayerPrefs`는 Android에서 SharedPreferences XML 평문, iOS에서 NSUserDefaults 평문입니다. 루팅/탈옥
기기나 기기 백업에서 읽힙니다. Keychain/Keystore는 안전하지만 Unity 기본 API로는 접근할 수 없어
네이티브 브리지가 필요합니다(Android는 androidx.security의 EncryptedSharedPreferences, iOS는 Keychain
Services).

여기서 먼저 물어야 할 건 "무엇을 지키는가"입니다. 액세스 토큰은 60분짜리라 유출 피해가 제한적이고,
장수명 자격(리프레시 토큰이든 게스트 시크릿이든)이 사실상 계정 그 자체입니다. 그리고 이 게임의
재화는 환전이 불가능하므로(`architecture.md` §5) 계정 탈취의 금전 피해는 없고, 전적·포인트 분실에
따른 CS 부담이 실질 피해입니다.

**권고: 장수명 자격만 Keychain/Keystore에 넣고 액세스 토큰은 메모리에만 둡니다. 다만 M3 단계에서는
PlayerPrefs로 먼저 내고, M5 안에 교체합니다.** M3의 목표가 "실기기에 올려서 플레이테스트가 가능한
상태"이고 그 시점 테스터는 내부 인원이라, 네이티브 브리지 작성 때문에 M3가 밀리는 게 더 손해입니다.
교체 시점에 바뀌는 건 저장소 어댑터 한 곳이므로 나중에 갈아끼우는 비용도 작습니다. 다만 이걸
"나중에"로 미루면 그대로 잊히기 쉬우니 M5 항목으로 못 박아 둡니다.

### 리프레시 전략

세 가지 안을 놓고 비교했습니다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 리프레시 토큰 테이블 + 회전 | 정석, 폐기 가능 | 테이블·엔드포인트·회전 로직 신규 |
| B | 액세스 토큰 수명을 30일로 연장 | 구현 없음 | 폐기 불가. 어뷰저 차단(R2)이 불가능해짐 |
| C | 저장된 자격으로 재로그인 | 소셜은 서버 변경 0 | 게스트는 자격 자체를 새로 만들어야 함 |

**권고는 C를 기본으로 하고 게스트에만 최소한의 A를 얹는 혼합안입니다.**

소셜 계정은 C로 충분합니다. Google/Apple SDK 모두 캐시된 credential로 조용한 재인증을 제공하므로,
액세스 토큰이 만료되면 provider에서 id 토큰을 다시 받아 `/auth/social`을 호출하면 됩니다. 서버는
`LoginWithSocialAsync`가 (provider, subject)로 기존 계정을 그대로 반환하므로(`AccountService.cs:42-46`)
변경이 필요 없습니다.

게스트는 재인증할 provider가 없으니 자격을 우리가 발급해야 합니다. 다만 여기에 refresh_tokens
테이블까지 만들 필요는 없습니다. `/auth/guest` 응답에 재사용 가능한 시크릿을 함께 내리고,
`/auth/guest/resume`(userId + secret)로 새 액세스 토큰을 받는 경로 하나면 됩니다. 서버 변경은
`users` 테이블에 시크릿 해시 컬럼 하나와 엔드포인트 하나입니다. 계정 정지가 필요하면 그 해시를
지우면 됩니다.

B는 채택하지 않습니다. 담합 탐지(R2) 결과 계정을 정지시켜야 할 때 폐기 경로가 없으면 손을 쓸 수
없습니다.

### 만료를 언제 어떻게 감지하나

지금 `ServerApi.Send`는 성공/실패만 구분하고 401을 특별 취급하지 않습니다(`ServerApi.cs:105-112`).
WebSocket 쪽은 조금 다른데, `/ws`는 업그레이드 시점에 한 번만 JWT를 검증하므로
(`WsEndpoint.cs:22-23`의 `RequireAuthorization`), 이미 열린 연결은 토큰이 만료돼도 끊기지 않습니다.
게임 중에 60분이 지나도 그 판은 무사히 끝납니다.

그래서 만료의 실질 피해는 REST 호출 실패와 재연결 실패 두 가지입니다. 대응도 그에 맞춰
두 군데면 됩니다. `ServerApi.Send`가 401을 받으면 갱신을 한 번 시도하고 원 요청을 재시도하도록
하고, `WsClient.Connect` 직전에 토큰 잔여 수명을 확인해 임계치 아래면 먼저 갱신합니다. 갱신
자체는 AppHost의 코루틴에서 돌아 화면 전환과 무관하게 동작합니다.

### 소셜 로그인 범위

Apple의 심사 지침상 다른 소셜 로그인을 하나라도 제공하면 Sign in with Apple을 함께 제공해야
합니다. 게스트만 있으면 해당하지 않지만, Google만 붙이고 iOS에 내면 리젝됩니다. `SocialProvider`
enum에 Google/Apple/Kakao가 이미 정의돼 있으므로(`SocialProvider.cs`) 서버 도메인은 준비돼 있고,
provider별 검증기와 클라 SDK 연동만 남았습니다.

Kakao는 국내 유저 접근성이 좋지만 iOS 출시 시점 판단 사항입니다. Android 우선 출시라면 Google과
Kakao로 시작하고, iOS 착수 시 Apple을 추가하는 순서가 자연스럽습니다.

### 게스트 → 소셜 승격과 계정 충돌

정상 경로는 `LinkSocialAsync`로 끝납니다. 계정 id와 잔액이 그대로 유지됩니다.

문제는 충돌 경로입니다. 연동하려는 소셜이 이미 다른 계정에 붙어 있으면 서버가 예외를 던지고
끝납니다(`AccountService.cs:64-68`). 유저 입장에서는 "이 기기에서 게스트로 놀았는데, 내 구글
계정에는 예전에 만든 계정이 이미 있다"는 상황이고, 두 계정 중 하나를 버려야 합니다.

**자동 병합(잔액 합산)은 하지 않습니다.** 신규 계정마다 10,000P가 지급되므로
(`AccountService.StartingGrant`), 게스트를 반복 생성해 초기 지급을 모은 뒤 소셜로 합치는 통로가
정확히 그 지점에서 열립니다. R2가 우려하는 재화 부정 축적과 같은 종류입니다.

대신 클라가 선택을 제시합니다. "기존 계정으로 로그인(현재 진행 상황은 사라집니다)" 또는 "취소"
두 가지이고, 전자는 `/auth/social`을 호출하면 됩니다. 서버 변경은 없고 클라 화면 하나입니다.

### 기기 변경 복구

소셜에 연동돼 있으면 `/auth/social` 한 번으로 복구됩니다. 게스트만이면 복구 수단이 없습니다.
지금 진입 흐름이 게스트를 기본으로 밀고 있어서(`AuthBootstrap.cs:43-50`) 방치하면 대다수가 게스트로
남습니다.

기술이 아니라 UX로 방어합니다. 잔액이나 누적 판수가 일정 수준을 넘으면 로비에 연동 유도를 띄우고,
포인트 보너스를 붙이는 게 흔한 방식입니다. 로드맵의 "게스트를 계속 허용하되 소셜 연동을 강하게
유도"와 같은 결론이고, 구현은 M6의 경제 밸런싱과 같이 다루면 됩니다.

## 3. 서버 확장성과 배포

### 지금 어떻게 돼 있나

`RoomRegistry`는 `ConcurrentDictionary` 두 개(코드→방, 유저→방)로 된 싱글턴이고
(`RoomRegistry.cs:13-14`, `Program.cs:45`), 프로세스 메모리 위에 있습니다. `Room`은 커맨드 채널
하나와 단일 소비 루프로 모든 입력을 직렬화하며(`Room.cs:26`, `:97-111`), 참가자·봇·이탈자·좌석
매핑·게임 세션을 전부 필드로 들고 있습니다. 타이머도 `Task.Run` + `Task.Delay` 조합이라
프로세스에 묶여 있습니다(`Room.cs:648-653`). `RoomMember`는 실제 WebSocket을 감싼 sink를 들고
있고(`WsEndpoint.cs:49-50`), 소켓은 당연히 프로세스 로컬입니다.

배포는 `fly deploy --ha=false`로 머신 1대를 고정하고, `auto_stop_machines = "off"`,
`min_machines_running = 1`입니다(`fly.toml`). 배포하면 진행 중인 방이 전부 사라집니다.

이 게임의 특성도 같이 놓고 봐야 합니다. 한 세트는 5판이고(`GameConfig.DefaultSetRounds`), 턴 제한
5초, 뽕 창 5초, 판 사이 8초입니다(`RealtimeConfig`). 방당 2~6명이고 세트가 끝나면 판돈 방은 즉시
폭파됩니다(`Room.cs:534-560`). 방 하나의 수명은 10분 안팎으로 추정하는데, 정확한 수치는
`scripts/quickmatch-storm.py` 실행 로그에 있을 수 있으므로 드레인 시간 산정 전에 실측이 필요합니다
(확인 필요).

### 선택지 비교

**A. 방 상태 외부화(Redis 등).** `Room`과 `GameSession`의 상태를 전부 직렬화해 외부 저장소에 두고
커맨드마다 로드·저장·락을 겁니다. 진짜 수평 확장이 되고 머신이 죽어도 방이 살아남습니다. 다만
`Room.cs` 712줄과 `GameSession.cs` 975줄의 상태 모델을 전부 손봐야 하고, 더 큰 문제는 소켓이
여전히 프로세스 로컬이라는 점입니다. 상태는 공유인데 전송은 로컬이므로 다른 머신에 붙은 참가자
에게 메시지를 보내려면 pub/sub 팬아웃 계층이 추가로 필요합니다. 규모가 큽니다.

**B. 세션 어피니티.** 방 코드를 일관 해시나 fly-replay로 특정 머신에 고정하고 상태는 인메모리로
둡니다. 그런데 지금 흐름에서는 성립하지 않습니다. 클라가 `/ws`에 먼저 붙고 그 위에서
`createRoom`/`joinRoom`을 보내므로(`FriendRoomBootstrap.cs:181`, `:191`) 연결 시점에는 어느 방인지
모릅니다. 빠른매칭은 더 심해서 서버가 방을 고릅니다(`RoomRegistry.QuickMatch`). 어피니티를 하려면
방 배정을 연결 전 단계로 끌어올려야 하고 이는 프로토콜 변경입니다. 게다가 확장은 되지만 배포
문제는 그대로입니다. 해당 머신이 내려가면 그 방들은 여전히 죽습니다.

**C. 무중단 드레인.** 신규 방 생성·입장을 막고, 진행 중인 방이 전부 끝나기를 기다린 뒤 교체합니다.
`RoomRegistry`에 플래그와 방 수 조회를 추가하고 `WsEndpoint`에 분기를 넣는 정도이므로 규모가
작습니다. 한계는 드레인 대기 시간이 가장 긴 진행 중 세트에 묶인다는 것과, 크래시에는 무력하다는
것입니다.

### 권고: C를 하고 A는 지금 하지 않습니다

이유는 셋입니다.

방 수명이 10분 내외로 짧아 드레인 대기가 현실적입니다. 한 시간씩 기다릴 일이 없습니다.

턴제에 방당 2~6명, 5초 타이머라 단일 머신의 여유가 큽니다. shared-cpu-1x 512MB 한 대에서 100인
동시 접속 폭풍 테스트를 세 번 완주했고 이상이 없었습니다(worklog 2026-08-09). 수평 확장이 필요한
시점이 아직 오지 않았습니다.

A는 사실상 Room/GameSession 재작성인데, 이걸 M5에 넣으면 출시가 밀립니다. 그리고 그 복잡도를
감당해야 할 만한 동시 접속 수치가 아직 없습니다. 유저가 붙어서 단일 머신이 모자라는 게 확인되면
그때 하는 게 맞습니다.

### 크래시로 방이 사라지면 에스크로는 어떻게 되나

드레인은 정상 배포를 커버하지만 크래시는 못 막습니다. 여기서 하나 짚어둘 게 있습니다.

판돈 방의 입장료는 `IStakeBank.TryEscrowAsync`로 원장에 차감이 기록되고
(`WsEndpoint.cs:112`, `:127`, `:143`), 정산은 세트 종료 시에만 일어납니다(`Room.cs:534-560`). 그런데
이 경로는 `matches` 테이블을 쓰지 않습니다. `matches`는 `/match/start`~`/match/{id}/result`
싱글 봇전 전용입니다(`MatchService`). 즉 로드맵 M5-2의 "미정산 매치 타임아웃 정리 잡"이
`matches`만 청소한다면, 크래시로 사라진 실시간 방의 에스크로는 회수되지 않습니다.

다행히 복구 근거는 있습니다. 게임 시작 시 `games` 행과 `game_players` 행이 만들어지고
(`Room.cs:460-469`), 종료 시에만 `CompleteGameAsync`가 완료 시각을 채웁니다. 그러니
**종료 시각이 비어 있고 시작한 지 충분히 오래된 `games` 행을 골라 참가자에게 stake를 환불하는
정리 잡**이면 됩니다. 매 게임의 참가자와 stake가 그 테이블에 다 있습니다. 이 정리 잡은 M5 항목으로
잡되, 대상이 `matches`와 `games` 둘이라는 점을 명확히 해야 합니다.

### 구체적으로 어디를 고치나

`RoomRegistry`에 드레인 상태를 둡니다. `Draining` 속성과 `Drain()` 메서드, 그리고 활성 방 수
조회입니다. 방 수는 `_rooms.Count`로 충분한데, `Room.CloseRoom`이 이미 `_registry.Remove(Code)`를
부르고 있어서(`Room.cs:666`) 방이 닫히면 자동으로 빠집니다.

`WsEndpoint.RouteAsync`의 세 케이스(`QuickMatchMsg`, `CreateRoomMsg`, `JoinRoomMsg`)에서 드레인
중이면 거절합니다. **주의할 점은 검사 위치입니다.** 세 경로 모두 `TryEscrowAsync`로 먼저 판돈을
차감하므로(`WsEndpoint.cs:112`, `:127`, `:143`), 검사를 그 앞에 두지 않으면 차감해 놓고 거절하는
일이 생깁니다.

`Program.cs`에는 `/health`를 추가합니다. 활성 방 수와 드레인 여부를 JSON으로 내면 배포 스크립트와
외부 모니터가 같이 씁니다. 운영자용 드레인 트리거도 필요한데, `IHostApplicationLifetime.ApplicationStopping`
훅에서 `Drain()`을 호출하고 방이 0이 될 때까지 대기하는 형태면 별도 엔드포인트 없이도 됩니다.

클라는 에러 표시 경로가 이미 있으므로(`FriendRoomBootstrap.cs:243-250`) 새 에러 코드에 맞는 문구만
추가하면 됩니다. "잠시 후 다시 시도해 주세요" 수준이면 충분합니다.

fly의 blue/green 배포(`--strategy bluegreen`)를 `--ha=false` 단일 머신 구성과 조합했을 때 어떻게
동작하는지는 확인이 필요합니다(확인 필요). 안 되면 드레인 후 순차 교체로 가되, 그 사이 신규 매칭이
막히는 창이 생깁니다.

## 4. 클라이언트-서버 프로토콜의 앞날

### 지금 구조가 이미 가진 성질

메시지는 `{type, ...}` 평면 엔벨로프이고, 서버는 type을 먼저 읽고 타입별로 재파싱하는 2-pass
방식입니다(`RealtimeJson.ParseClientMessage`). 모르는 type은 null이 되어 `bad_message` 에러를
돌려줍니다(`WsEndpoint.cs:84-89`). 클라는 `JsonUtility.FromJson<ServerEnvelope>`로 type을 보고
switch를 도는데, default 케이스가 없어 모르는 type은 조용히 무시합니다
(`NetGameTableBootstrap.cs:74-243`, `FriendRoomBootstrap.cs:214-252`).

이 비대칭이 실은 유리하게 작용합니다. **서버가 새 메시지 타입을 추가해도 구버전 앱은 무시하고
넘어갑니다.** 필드 추가도 마찬가지로, `JsonUtility`는 모르는 필드를 무시합니다. 반대로 클라가 새
타입을 보내면 구버전 서버가 거절하지만, 서버는 우리가 언제든 배포할 수 있으니 문제가 되지
않습니다. 즉 위험한 방향은 "신버전 서버 + 구버전 앱" 하나뿐이고, 그 방향이 이미 안전합니다.

깨지는 경우는 셋으로 좁혀집니다. 기존 필드의 의미나 타입을 바꾸는 것, 기존 메시지를 없애는 것,
그리고 서버가 새로운 클라 메시지를 필수로 요구하게 되는 것입니다.

### 호환성 정책

세 가지를 규칙으로 정합니다.

**필드는 추가만 합니다.** 삭제와 의미 변경은 금지합니다. 동작이 달라져야 하면 새 type을 추가하고
기존 type은 그대로 둡니다. 이것만 지키면 구버전 앱은 계속 돌아갑니다.

**앱 버전을 서버가 알 수 있게 합니다.** 지금 프로토콜에 버전 정보가 전혀 없습니다. `WelcomeMsg`에는
userId만 들어 있습니다. 여기서 새 `hello` 클라 메시지를 도입하면 그것 자체가 구버전 서버에서
거절되는 종류의 변경이라, 더 싼 방법을 씁니다. WebSocket URL 쿼리에 앱 버전을 얹으면 됩니다.
`/ws?access_token=...&cv=1.2.0` 형태이고, 클라 변경은 `WsClient.cs:97`과 `:167` 두 줄, 서버는
`HttpContext.Request.Query`에서 읽으면 됩니다. 구버전 서버는 모르는 쿼리를 무시하므로 무해합니다.
**이건 M3에 미리 심어두는 게 좋습니다.** 나중에 넣으면 그 시점의 구버전 앱들은 영영 버전을 못
알립니다.

**강제 업데이트 대신 기능 단위 차단을 씁니다.** 스토어 심사 지연 때문에 즉시 강제 업데이트는
불가능합니다. 대신 서버가 특정 앱 버전에 대해 특정 모드만 막고 나머지는 허용하는 방식이면
심사를 기다리는 동안에도 사고를 국소화할 수 있습니다. 최후 수단으로 최소 지원 버전 미만은
로그인 자체를 거절하되, 이건 프로토콜이 실제로 깨졌을 때만 씁니다.

이 두 가지(기능 차단, 최소 버전)를 클라에 내리려면 서버가 클라에 설정값을 내려주는 경로가
필요한데, 지금 그런 경로가 없습니다. §8의 판돈 스위치도 같은 것을 필요로 하므로 한 번에
만듭니다. `/me` 응답에 `features` 객체를 얹는 게 가장 싼데, 로그인 직후와 로비 복귀 때마다 반드시
호출되기 때문입니다(`AuthBootstrap.cs:65`, `MainLobbyBootstrap.cs:19`).

### 재연결

서버는 이미 준비돼 있습니다. 게임 중 끊김은 좌석을 보전하고(자발적 나가기만 즉시 봇으로 대체
— `Room.cs:317-334`), 다시 `joinRoom`을 보내면 `Reconnect`가 새 소켓으로 좌석을 복구하고
`GameStartedMsg`와 현재 상태를 재전송합니다(`Room.cs:281-297`, `GameSession.cs:850-869`). 판돈 방의
재입장료 이중 청구도 막혀 있습니다(`WsEndpoint.cs:143`의 `HasSeatFor`). `Room.cs:320`의 주석에
"끊김(앱 백그라운드 가능성)은 판 종료까지 자리 보전"이라고 이미 적혀 있습니다.

빠진 건 클라입니다. `HandleClosed`는 진입 화면으로 돌아가거나 로비로 나가버립니다
(`FriendRoomBootstrap.cs:254-259`, `NetGameTableBootstrap.cs:246-252`). 재연결 시도 자체가 없습니다.

필요한 것은 셋입니다. 끊김을 감지하면 지수 백오프로 자동 재연결하고(0.5초부터 시작해 30초 한도
정도), 재연결에 성공하면 마지막 방 코드로 `joinRoom`을 다시 보내고, 그동안 화면은 파괴하지 않고
"재연결 중" 오버레이를 띄웁니다.

**여기서 걸림돌이 하나 있습니다.** 재연결하려면 방 코드를 알아야 하는데, 게임 테이블이 그걸
모릅니다. `FriendRoomBootstrap`은 `RoomUpdateMsg.code`를 받아 보관하지만
(`FriendRoomBootstrap.cs:220`), 게임이 시작되면 자신을 파괴하면서 좌석·인원·닉네임·판돈만 넘깁니다
(`FriendRoomBootstrap.cs:224-234`). `GameStartedMsg`에도 방 코드 필드가 없습니다
(`ServerMessages.cs`의 `GameStartedMsg`). 재연결을 구현하려면 `GameStartedMsg`에 `code`를 추가하거나
핸드오프에 실어야 합니다. 전자가 재접속 경로에서도 자동으로 채워지므로 낫습니다.

부수적으로, `NetGameTableBootstrap`에는 `GameStarted` 케이스가 없습니다. 재접속 시 서버가
`GameStartedMsg`를 다시 보내는데(`Room.cs:288-295`) 테이블이 이미 살아 있는 상태에서 받으면
처리할 곳이 없습니다. 재연결을 붙일 때 이 케이스를 추가해 뷰를 리셋해야 이전 판의 잔상과 새
상태가 섞이지 않습니다.

### 백그라운드 전환

`WsClient`가 `Application.runInBackground = true`를 켜지만(`WsClient.cs:63`), 모바일 OS는 백그라운드
앱의 소켓을 유지해주지 않습니다. iOS는 수 초 내에 정지시키고 Android도 Doze와 네트워크 제한이
걸립니다. 애매하게 살아 있는 소켓을 붙들고 있는 것보다 **백그라운드 진입 시 명시적으로 끊고 복귀
시 재연결하는 편이 예측 가능합니다.** 서버가 끊김을 판 종료까지 좌석 보전으로 처리하므로 이쪽이
서버 설계와도 맞습니다.

셀룰러와 Wi-Fi 사이를 오가면 IP가 바뀌어 TCP 연결이 죽는데, 위의 자동 재연결이 그대로 커버합니다.

### 메시지 유실은 대비하지 않습니다

끊긴 동안의 이벤트는 재전송되지 않습니다. `HandleReconnect`는 현재 상태 스냅샷만 보냅니다
(`GameSession.cs:867`의 `TurnBeganMsg` + `BuildView`). 이게 올바른 설계입니다. 이 게임은 좌석별
상태 스냅샷이 곧 진실이고, 놓친 것은 연출뿐입니다. 카드가 날아가는 애니메이션을 못 본 게 게임
진행에 영향을 주지 않습니다.

**따라서 이벤트 재생 버퍼나 시퀀스 번호 기반 재전송은 만들지 않습니다.** 스냅샷 재동기화로
충분하고, 버퍼를 만들면 그것을 어디에 얼마나 보관할지가 곧바로 상태 외부화 문제로 번집니다.

## 5. 빌드와 배포 파이프라인

### 지금 어떻게 돼 있나

Unity 쪽은 `CliBuild.WebGL` 하나뿐이고 Android/iOS 진입점이 없습니다(`CliBuild.cs`). Pages 워크플로는
`webgl/` 폴더가 푸시되면 배포만 할 뿐(`pages.yml`), Unity 빌드 자체는 로컬 수동입니다. 서버는
`fly deploy --ha=false` 수동입니다.

플레이어 설정은 로드맵 5번에 정리된 대로 전부 기본값입니다. 확인한 값은 다음과 같습니다.

| 항목 | 현재 값 |
|---|---|
| companyName | DefaultCompany |
| productName | BBongClient |
| applicationIdentifier | 비어 있음 |
| bundleVersion / AndroidBundleVersionCode | 1.0 / 1 |
| AndroidMinSdkVersion / TargetSdkVersion | 25 / 0(자동) |
| 화면 방향 | 가로 고정(세로 회전 비활성) |
| scriptingBackend | 미지정(플랫폼 기본) |

Unity 버전은 6000.4.10f1입니다. `com.unity.purchasing` 5.4.2가 들어와 있으나 미사용이고,
`com.unity.services.cloud-build`도 들어와 있습니다.

### CI를 도입할 것인가

Unity 빌드를 GitHub Actions에서 돌리려면 GameCI에 라이선스 activation, Android IL2CPP 빌드 15~30분,
iOS는 분당 요금이 훨씬 비싼 macOS 러너가 필요합니다. 초기 설정 비용이 작지 않습니다. 반면 얻는
것은 재현성과 서명 키 중앙 관리, 스토어 트랙 자동 업로드인데, 이 이득은 릴리스가 잦아야 커집니다.
출시 전 단계에서 릴리스가 월 1~2회라면 로컬 빌드로 충분합니다.

**권고는 단계적 도입입니다.**

먼저 지금 할 것은 `CliBuild`에 `Android()`와 `iOS()` 메서드를 추가하고 얇은 셸 스크립트로 감싸는
것입니다(`scripts/build-android.sh`). 버전 코드 자동 증가도 여기서 처리합니다. 규모가 작고 이득이
즉각적입니다. 로컬 빌드라도 재현 가능한 명령 한 줄이 되면 "빌드할 때마다 에디터 설정을 만졌던가"
같은 사고가 사라집니다.

두 번째로 서버 테스트만 CI에 올립니다. `dotnet test`는 무료 러너에서 5분이면 끝나고, 코어 131개와
서버 163개 테스트가 이미 있으니 회귀 방어 효과가 바로 나옵니다. 이건 지금 해도 됩니다.

Unity CI는 M7 전후, 릴리스 빈도가 올라간 뒤에 GameCI로 붙입니다. 그전까지는 하지 않습니다.

### 서명과 버전 정책

Android 업로드 키스토어는 레포에 넣지 않고 로컬에 두되 반드시 백업합니다. 잃으면 앱 업데이트가
불가능해집니다. Play App Signing에 등록하면 배포 키는 구글이 관리하고 우리는 업로드 키만 관리하면
되므로 사고 여지가 줄어듭니다. iOS는 Xcode 자동 서명으로 시작합니다.

버전은 두 축으로 나눕니다. `bundleVersion`은 마케팅 버전(1.0.0)이고, `AndroidBundleVersionCode`와
iOS 빌드 번호는 단조 증가하는 정수입니다. 빌드 스크립트가 후자를 올리고 커밋합니다. §4의 프로토콜
버전은 이것과 별개로 관리합니다. 앱 버전이 올라도 프로토콜이 그대로면 프로토콜 버전은 유지합니다.

패키지 ID는 한 번 올리면 못 바꾸므로 상표 검토(R5)와 같이 정합니다. `applicationIdentifier`가 아직
비어 있다는 건 오히려 다행이라, 지금 정하면 됩니다.

## 6. 관측성과 운영

### 지금 어떻게 돼 있나

서버에 `ILogger` 사용처가 한 건도 없습니다. 헬스체크 엔드포인트도 없습니다. 로그는 기본 콘솔
출력이 `fly logs`로 나가는 게 전부입니다. 클라에는 크래시 리포팅이 없습니다.

반면 게임 히스토리는 잘 갖춰져 있습니다. 게임 메타·좌석별 참가자·라운드 이벤트 전체가
`games`/`game_players`/`game_events`에 기록되고(`IGameHistoryStore`, `EfGameHistoryStore`), 조회 API도
있습니다(`/me/games`, `/games/{gameId}/events` — `Program.cs:98`, `:129`).

### 우선순위

**1순위는 클라 크래시 리포팅입니다.** 없으면 출시 후에 아무것도 볼 수 없습니다. 유저가 "게임이
꺼져요"라고 하면 그걸로 끝입니다. Unity Cloud Diagnostics가 패키지 추가와 프로젝트 연결만으로
시작할 수 있어 가장 쌉니다(`UnityConnectSettings.asset`이 있으므로 조직 연결 여부만 확인하면 됩니다,
확인 필요). Firebase Crashlytics가 더 강력하지만 의존성이 커서 지금은 과합니다.

**2순위는 서버 로그입니다.** 여기서 하나 짚어둘 게 있는데, `Room.RunLoopAsync`의 catch가 예외를
받아 `CloseRoom`으로 수렴시키는데 로그를 남기지 않습니다(`Room.cs:105-109`). 방이 조용히 죽고
원인이 아무 데도 안 남습니다. 진행 중인 판이 통째로 날아가는 경로인데 사후 추적이 불가능하다는
뜻이라, 여기가 제일 급합니다. 최소한 예외 내용과 방 코드를 남겨야 합니다.

그 밖에 남길 가치가 있는 것은 방 생성/종료, 정산 실패, WS 연결 수, 에러 코드별 카운트입니다.
`SafeSendAsync`(`Room.cs:701-711`)와 히스토리 체인(`Room.cs:594-613`)의 catch도 지금 전부 조용히
삼키고 있는데, 이쪽은 게임 진행과 무관한 실패라 카운터 정도면 됩니다.

**3순위는 지표와 알림입니다.** Prometheus/Grafana까지는 지금 필요 없습니다. `/health`가 활성 방 수와
접속 수를 JSON으로 내면 fly 기본 메트릭(CPU/메모리)과 합쳐 외부 모니터링 서비스로 충분합니다.
알림이 필요한 건 서버가 죽었을 때, 에러율이 튀었을 때, 정산이 실패했을 때 정도입니다.

**4순위는 CS 도구입니다.** 히스토리 조회 API가 본인 참여 게임만 허용하므로(`Program.cs:139-143`)
운영자가 "이 유저의 이 게임에서 무슨 일이 있었나"를 볼 수 없습니다. 새 관리자 UI를 만들 필요는
없고, 운영자 권한으로 같은 엔드포인트를 우회하는 경로 하나면 시작할 수 있습니다. 그것도 없으면
`psql` 직접 조회로 버팁니다. 이벤트가 JSONB로 원문 그대로 저장돼 있어서(`Outbound.cs`의
`UnsafeRelaxedJsonEscaping` — 한글 원문 저장) 사람이 읽을 수 있습니다.

**5순위는 계정 삭제 경로입니다.** Play와 App Store 모두 앱 내 삭제 요청 경로와 웹 경로를 요구하므로
출시 필수 항목입니다. 원장은 회계·분쟁 대응 근거라 통째로 지우면 안 되고, 계정 행을 tombstone으로
바꾸고 닉네임과 소셜 subject를 제거하는 익명화가 실무적입니다. 원장 항목은 userId만 남습니다.

## 7. 판돈 시스템의 조건부 설계

### 지금은 스위치 하나로 끌 수 없습니다

판돈이 나타나는 지점을 전부 훑었습니다.

| 계층 | 위치 |
|---|---|
| 코어 | `GameConfig.StakeOptions`(6단계), `IsValidStake`, `BankruptcyThreshold`, `StakePot.Share/Distribute` |
| 서버 실시간 | `WsEndpoint.cs:106-159`(세 경로의 에스크로), `Room.Stake`, `Room.cs:534-560`(정산), `IStakeBank`/`LedgerStakeBank` |
| 서버 REST | `MatchService`(`/match/start`, `/match/{id}/result`), `ShopService`(광고 보상·파산 구제) |
| 클라 | `MatchSetupBootstrap.cs:74-75`(입장료 선택), `:128`(총상금), `FriendRoomBootstrap.cs:103-108`, `NetGameTableBootstrap.cs:199-201`, `MainLobbyBootstrap.cs:29-31`(맞춤게임 카드) |

좋은 소식은 "판돈 0 = 무료방" 경로가 이미 전 계층에 흐른다는 것입니다. 무료 친구방이 정확히 그
경로이고 실제로 동작합니다. `IsValidStake`는 `StakeOptions`에 0이 없어서 false를 내지만,
`CreateRoom` 핸들러가 `create.stake != 0 && !IsValidStake(...)` 형태로 0을 예외 취급합니다
(`WsEndpoint.cs:121`).

나쁜 소식은 이걸 끄는 단일 지점이 없다는 것입니다. 서버에서 판돈을 거절하려면 세 경로를 각각
막아야 하고, 클라의 맞춤게임 모드는 판돈 선택을 전제로 만들어져 있어(`MatchSetupBootstrap.cs:22`의
기본값 1000) 판돈을 빼면 모드가 통째로 의미를 잃습니다. 게다가 입장료 목록을 클라가 코어 상수에서
직접 읽고 있어서(`MatchSetupBootstrap.cs:74`) 목록을 줄이려면 앱을 다시 배포해야 합니다.

### 필요한 구조

**서버가 권위인 판돈 정책 객체와, 그것을 클라가 읽어 UI를 접는 경로** 두 가지입니다.

서버 쪽은 `StakePolicy` 하나를 도입하고 환경변수로 모드를 읽습니다(`full` / `capped` / `off`).
DI 싱글턴이면 되고, 검증 지점을 `GameConfig.IsValidStake` 직접 호출에서 정책 객체 호출로 바꿉니다.
코어의 `IsValidStake`는 규칙 상수라 그대로 두고, 서버가 그 위에 정책을 얹는 형태입니다.

- `off`: `WsEndpoint`의 세 경로에서 stake > 0을 전부 거절합니다. `Room`, `GameSession`, `StakePot`은
  손대지 않습니다. stake = 0 경로가 이미 완전히 동작하기 때문입니다.
- `capped`: 허용 입장료를 부분집합으로 줄이고, 필요하면 일일 손실 한도를 검사합니다. 한도 검사는
  원장에 모든 변동이 기록돼 있으므로 조회로 계산할 수 있습니다. 다만 일일 집계 쿼리가 새로
  필요하므로 규모가 중간입니다.
- `full`: 지금 동작 그대로입니다.

클라 쪽은 `/me` 응답의 `features`에 `stakeEnabled`와 `stakeOptions[]`를 실어 내립니다(§4에서 만든
그 경로입니다). `MainLobbyBootstrap`이 `stakeEnabled`가 false면 맞춤게임 카드를 감추고,
`MatchSetupBootstrap`이 입장료 목록을 코어 상수 대신 서버 값으로 채웁니다. 구조 변경은 이 두
군데뿐입니다.

이렇게 하면 **앱 재배포 없이 서버 환경변수만으로 판돈을 끄고 켤 수 있습니다.** GRAC 결과가 언제
나올지 모르는 상황에서 이게 결정적입니다.

### 1차 출시를 판돈 없이 내는 선택지

위 구조를 미리 넣어두면 "판돈 없이 출시 → 분류 확정 후 서버 플래그만 켜기"가 스토어 재심사 없이
가능해집니다. 로드맵이 검토 중인 선택지가 실제로 성립하게 되는 조건이 이 구조입니다.

다만 두 가지가 남습니다. 나중에 판돈을 켤 때 앱 설명과 스크린샷 등 스토어 메타데이터 갱신은
필요합니다. 그리고 등급 분류는 잠재적 기능까지 보는 경우가 있어서, 판돈 코드가 들어 있는 앱을
"판돈 없음"으로 신고하는 것이 문제가 되지 않는지는 법무 확인이 필요합니다(확인 필요). 만약
문제가 된다면 판돈 코드를 조건부 컴파일로 아예 빌드에서 빼는 방법이 있는데, 그러면 나중에 켤 때
재심사가 필요해져 이 구조의 이점이 사라집니다. 법무 확인 결과에 따라 갈리는 지점이라 미리
결정하지 않습니다.

**권고는 플래그 구조를 M3~M4 사이에 넣는 것입니다.** 규모가 작고(off 모드만이면 작음, capped까지면
중간), 넣어두면 이후 모든 선택지가 열린 채로 유지됩니다. 1차 출시 판돈 포함 여부는 GRAC 결과를
기다리되, M7 착수 시점까지 결과가 안 나오면 `off`로 출시합니다.

## 9. 지금은 하지 않는 것

과잉 설계를 피하기 위해 검토한 뒤 접은 것들입니다. 나중에 필요해질 수 있지만 지금 넣으면
검증되지 않은 복잡도만 남습니다.

**방 상태 외부화(Redis).** 단일 머신으로 100인 동시 접속을 감당하고 있고, 방 수명이 짧아 드레인
배포로 충분합니다. 필요해지는 시점은 단일 머신이 실제로 모자란다는 지표가 나올 때입니다.

**세션 어피니티 라우팅.** 지금 프로토콜에서는 연결 시점에 방을 모르기 때문에 성립하지 않고,
배포 문제도 해결하지 못합니다.

**씬 분리, DI 컨테이너, 상태머신 프레임워크, UI 프리팹화.** 코드 생성 UI는 이미 화면 20개 가까이를
감당하고 있고 2차 디자인 리뷰까지 통과했습니다. 지금 바꿀 이유가 없습니다.

**이벤트 재생 버퍼와 시퀀스 기반 재전송.** 상태 스냅샷 재동기화가 이 게임에는 정확한 해법이고,
버퍼를 만들면 곧바로 상태 외부화 문제로 번집니다.

**리프레시 토큰 테이블(회전형).** 소셜은 provider 재인증으로, 게스트는 시크릿 하나로 해결됩니다.
테이블과 회전 로직은 그만한 이득이 없습니다.

**Unity CI.** 출시 전 릴리스 빈도에서는 로컬 빌드 스크립트로 충분합니다.

**SignalR 전환.** 순수 WebSocket이 잘 돌고 있고 WebGL 브리지까지 만들어 뒀습니다. 바꿀 이유가
없습니다.

**Prometheus/Grafana, 관리자 웹 콘솔.** `/health` + fly 메트릭 + psql로 시작합니다.

**마이크로서비스 분리.** `architecture.md` §3의 판단(모듈러 모놀리식)이 여전히 유효합니다.

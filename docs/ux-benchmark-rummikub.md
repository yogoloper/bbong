# 루미큐브 벤치마크 — 우리 앱에 적용할 것과 미룰 것

작성 2026-08-13. 비교 대상은 Rummikub 모바일(로비 / 세팅 / 전적-통계 / 전적-게임기록) 4개 화면.

우리 게임은 2~6인 턴제 카드 게임에 판돈 포인트를 걸고, 전체이용가를 전제로 한다.
루미큐브는 같은 장르지만 레벨·토너먼트·유료 코인이 붙은 오래된 라이브 서비스라,
겉모습을 그대로 옮기면 우리에겐 과한 부분이 많다. 아래는 "왜 우리에게 필요한가"를
따진 뒤 남은 것들이다.

관련 문서: [모바일 로드맵](mobile-roadmap.md), [아키텍처](mobile-architecture.md), [DB 스키마](db-schema.md)

---

## A. 이번에 구현한 것

### A-1. 설정을 화면이 아니라 오버레이로 (완료)

루미큐브의 세팅은 오른쪽에서 덮는 패널이고, 뒤 화면은 살아 있다.

처음엔 우리도 설정을 독립 화면으로 만들었는데, 그러면 친구방·매칭 대기에서 열 수 없다.
캔버스를 버리고 로비로 넘어가면 방 연결만 남고 상태가 어긋나기 때문이다. 실제로 그
이유로 두 화면에서는 진입점을 숨겨야 했다.

오버레이(`SettingsBootstrap`, sortingOrder 500 + 스크림)로 바꾸고 나니 제약이 사라져서,
게임 테이블 우상단에도 진입점을 뒀다. 판이 도는 중에 소리를 끄는 건 실제로 자주 필요하다.

### A-2. 기록에 승/패 대신 등수 (완료)

루미큐브 게임기록은 `1st` / `4th`로 순위를 보여준다. 우리는 승/패 두 값뿐이었는데,
2~6인 게임에서 이건 정보가 너무 적다. 4인전 2등과 6인전 2등은 다른 판이다.

`GET /me/history`가 `rank`를 계산해 내려주고 화면에는 `2/3` 형태로 사람 수와 함께 표시한다.
순위는 좌석별 최종 빚(`FinalDebt`) 오름차순이며, 동점자는 같은 등수를 나눠 갖는다 —
우리 규칙상 공동 1등이 실제로 나오고 그때 둘 다 상금을 받기 때문이다.

구현 중에 걸린 함정 하나: 처음엔 봇을 포함한 좌석 전체로 등수를 매겼더니 실제 기록에서
"이겼는데 3등"이 나왔다. 이탈 대체 봇은 우승 후보에서 빠지는 규칙(§9-4)이라, 빚이 더
적은 봇이 있어도 남은 사람이 우승한다. 그래서 등수는 사람 좌석끼리만 매긴다.

사람이 나 혼자인 판(봇전)은 등수가 늘 `1/1`이라 의미가 없어 승/패로 표시한다.
인원 표시는 봇을 포함한 총 좌석 수를 그대로 쓴다 — 4인전은 4인전이다.

### A-3. 함께 플레이한 사람 표시 (완료)

루미큐브 기록은 같은 판에 있던 사람들의 닉네임을 나열한다. "누구랑 했더라"가
판을 떠올리는 가장 빠른 실마리라서 우리도 넣었다. `opponents`로 내려준다.

### A-4. 인원 계산의 근거를 좌석 수로 (완료)

정원(`TargetPlayers`)은 친구방에서 0이고, 매칭에서도 중도 이탈이 있으면 실제로
앉은 인원과 어긋난다. `game_players` 행 수로 센다.

## B. 참고만 하고 지금은 넣지 않은 것

### B-1. 통계/게임기록 탭 분리

루미큐브는 전적을 `통계` / `게임 기록` 두 탭으로 나누고, 통계 쪽은 다시
`모든 게임들 / 멀티플레이어 / 싱글 플레이어` 필터를 둔다.

우리 데이터로는 아직 탭을 나눌 만큼 항목이 많지 않다(전적 4개, 기록 8줄). 가로 화면
한 장에 좌우로 놓는 편이 탭 전환보다 빠르다. 항목이 늘면 그때 나눈다.

다만 필터 축은 이미 데이터에 있다 — `games.Mode`로 맞춤게임/친구와 함께를 가를 수 있다.
지금은 "맞춤게임 기준" 한 줄 안내로 대신한다.

### B-2. 총 게임 시간 · 평균 순위 같은 파생 통계

루미큐브는 `점수`, `xp`, `총 게임 시간`까지 쌓아 보여준다. 우리는 `StartedAtUtc`/
`EndedAtUtc`가 있으니 총 플레이 시간은 지금도 낼 수 있고, 평균 등수도 A-2에서
만든 순위 계산을 재사용하면 나온다.

넣지 않은 이유는 화면이 아니라 의미다. 표본이 한두 판인 계정에서 "평균 등수 2.0"은
읽는 사람을 오해시킨다. 판수가 쌓인 뒤(예: 10판 이상) 노출하는 게 맞다.

## C. 서버·기획이 선행되어야 하는 것

우선순위 순.

### C-1. 소셜 연동 진입점 — 높음

루미큐브 세팅 하단에는 `계정 동기화`가 있다. 우리는 게스트 계정이 기기 PlayerPrefs의
복구 시크릿에만 매여 있어서, 앱을 지우면 포인트와 전적이 함께 사라진다. 서버는
`LinkSocial`까지 준비돼 있는데 클라이언트에 붙이는 화면이 없다.

스토어 출시 전에 반드시 필요하다. 결제(포인트 구매)를 붙이면 더더욱 — 산 포인트가
날아가는 사고는 환불 분쟁으로 이어진다.

필요한 것: 클라이언트 소셜 로그인 SDK(Google / Apple), 설정 오버레이의 연동 버튼,
연동 후 게스트→정식 전환 안내.

### C-2. 랭킹 페이지 — 높음

루미큐브 상단에는 트로피 점수(9,235)가 상시 노출된다. 경쟁 지표를 항상 보여주는 게
재방문의 축이다.

우리는 포인트·승률·전적으로 랭킹을 만들기로 이미 정해 뒀다. 포인트 정렬을 위해
`accounts`에 잔액 캐시가, 승률 정렬을 위해 집계 뷰가 필요하다.

주의할 점 하나: 판돈 게임의 공개 랭킹은 전체이용가 심의에서 사행성으로 읽힐 소지가
있다. 포인트 랭킹보다 승률·판수 랭킹을 앞세우는 편이 안전하다.

### C-3. 레벨 / 경험치 — 중간

루미큐브는 `57,300 / 60K` 진행바를 상단에 상시 노출한다. 판을 이기지 못해도 뭔가
쌓인다는 감각이 이탈을 늦춘다.

우리도 판수 기반 레벨은 지금 데이터로 계산할 수 있지만, 레벨이 아무것도 잠금 해제하지
않으면 장식에 그친다. 보상 설계(레벨업 시 포인트 지급 등)가 먼저다.

### C-4. 언어 설정 — 중간

루미큐브는 세팅에서 언어를 고른다. 우리는 한국어 문자열이 코드에 박혀 있다.
해외 출시를 할 거라면 문자열 테이블 분리가 선행돼야 하고, 안 할 거라면 넣을 이유가 없다.
출시 시장을 정한 뒤 판단한다.

### C-5. 문의 / 서포트 — 중간

루미큐브 세팅에는 `서포트`가 있다. 스토어 등록 시 개발자 연락처는 필수라 최소한
이메일 주소 노출은 필요하고, 인앱 문의 폼까지는 지금 단계에선 과하다.

### C-6. 토너먼트 / 전용 게임 — 낮음

루미큐브 로비의 다섯 카드 중 둘이 이것이다. 동시 접속자가 모여야 성립하는 기능이라,
지금 규모에서는 빈 화면을 만드는 일이 된다. 유저가 쌓인 뒤 다시 본다.

### C-7. 로비 하단 상시 CTA — 낮음

루미큐브는 `무료 코인 모으기`를 하단 전체 폭으로 깔아 둔다. 우리는 `포인트 얻기`가
6개 카드 중 하나로 묻혀 있다.

다만 상시 노출은 부담을 준다. 잔액이 한 판 입장료 아래로 떨어졌을 때만 띄우는 편이
우리 게임에 맞는다. 이건 잔액 임계값 기획이 정해진 뒤에 붙인다.

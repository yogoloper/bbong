# BBONG 모바일 출시 로드맵

> 작성 2026-08-12, 갱신 2026-08-20. 웹(GitHub Pages + fly.io)은 해커톤 제출용 임시 경로이고,
> 최종 목표는 Google Play / App Store 출시입니다. 이 문서는 그때까지 남은 일을 정리한 것입니다.
> 규칙은 `rules.md`, 구조는 `architecture.md`, 리스크 대장은 `considerations.md`를 봅니다.
> 블로커 1~4는 2026-08-13 M3 작업(f5a8cf6)으로 해소됐고, 각 항목에 상태를 병기했습니다.

## 지금 어디까지 왔나

게임 자체는 사실상 완성돼 있습니다. 코어 룰 엔진(테스트 131개), 서버(163개), 클라이언트가 모두
돌아가고 웹에서 실제로 플레이됩니다.

- 규칙 전량 구현 — 뽕/자연뽕/족보 5종/스톱/스톱 바가지/뽕 바가지/쌍 공개/재셔플
- 모드 6종 — 튜토리얼(8레슨, 이전/다음 되감기 복습), 연습(봇 2~6인), 친구방(초대코드), 맞춤게임(포인트 매칭), 상점, 프로필(전적·기록)
- 서버 기반 실시간 멀티 — 좌석별 개인화 스냅샷, 5초 턴 타이머, 이탈 시 봇 대체, 재접속 복귀
- 판돈 흐름 — 지갑 락(PG advisory lock), 입장 에스크로, 이탈 몰수, 우승자 정산
- 게임 히스토리 DB — 딜 스냅샷부터 정산까지 전 이벤트 기록
- 100인 동시 접속 부하 테스트 3회 완주, 이상 0건
- UI 2차 디자인 리뷰까지 반영, 절차 생성 아이콘/카드아트

즉 남은 일은 "게임을 만드는 일"이 아니라 "앱으로 내보내는 일"입니다.

## 출시를 막는 것들

실기기에 올리기 전에 반드시 손봐야 하는 항목입니다. 근거가 되는 파일과 값을 같이 적었습니다.

### 1. 계정이 앱 재시작을 못 버팁니다 (최우선)

`Session.Token`이 그냥 static 필드라(`Session.cs:6`) 앱을 껐다 켜면 토큰이 사라집니다. 그러면
로그인 화면에서 "게스트로 시작"을 다시 누르게 되고, 그때마다 **새 계정이 생성**됩니다. 포인트도
전적도 통째로 날아갑니다. 웹에서는 탭을 안 닫으면 티가 안 났지만 모바일에서는 치명적입니다.

토큰을 PlayerPrefs(또는 Keychain/Keystore)에 저장하고, 시작 시 복원해서 자동 로그인하는 흐름이
필요합니다. 소셜 로그인 연동도 같은 맥락입니다. 기기를 바꿔도 계정을 잇는 유일한 수단이라
게스트 상태로만 두면 재설치 한 번에 유저를 잃습니다.

**✅ 해결(2026-08-13)** — 자격을 저장하고 시작 시 `ServerApi.ResumeLogin`으로 자동 복귀합니다.
저장 자격이 거부될 때만 버튼을 돌려주고 새 게스트는 만들지 않습니다. 남은 것은 기기 교체를
잇는 소셜 로그인뿐입니다.

### 2. 토큰이 1시간이면 만료되는데 갱신 경로가 없습니다

`JwtSettings.AccessTokenMinutes = 60`인데(`JwtSettings.cs:16`) 리프레시 토큰이 없습니다. 한 시간
넘게 앱을 켜두거나 백그라운드에 뒀다 돌아오면 API/웹소켓이 그냥 끊깁니다. 리프레시 토큰을 추가하거나,
최소한 만료 감지 후 저장된 자격으로 재로그인하는 처리가 있어야 합니다.

**✅ 최소 해법 적용(2026-08-13)** — 401 감지 시 저장 자격으로 자동 재로그인 후 재시도합니다
(`ServerApi` 공용 경로). 리프레시 토큰은 여전히 없으므로 보안 강화 여지로 남습니다.

### 3. Android 뒤로가기 버튼이 앱을 종료시킵니다

`Escape` 키(안드로이드 뒤로가기)를 아무 데서도 처리하지 않습니다. Unity 기본 동작은 즉시 종료라서,
게임 중에 뒤로가기를 누르면 판이 그대로 날아갑니다. 화면별로 "이전 화면", 게임 중에는 "나가기 확인
모달"로 연결해야 합니다. 스토어 심사에서도 자주 지적되는 항목입니다.

**✅ 해결(2026-08-13)** — `AppHost`가 `OnBackInvokedCallback`을 직접 등록하고(매니페스트 opt-in
포함, `docs/mobile-dev.md` 참고) 화면별 `UiKit.BackAction`으로 라우팅합니다. 게임 중엔 나가기
확인 모달, 최상위 화면에서만 앱 종료.

### 4. 노치·펀치홀 대응이 없습니다

`Screen.safeArea`를 쓰는 코드가 하나도 없습니다. 상단바가 화면 y 0.9~1.0, 나가기 버튼이 0.99까지
차지하는데(`UiKit.TopBar`, `GameTableView.BuildExitUi`) 최신 기기 가로 모드에서는 카메라 홀과
제스처 바에 물립니다. 캔버스 루트에 세이프에어리어 패널을 하나 끼우면 대부분 해결됩니다.

**✅ 해결(2026-08-13)** — `SafeArea.Wrap`이 캔버스 루트를 감쌉니다(세로만 대칭 인셋, 가로는
끝까지 사용). 배경·상단바 띠는 의도적으로 안전영역 밖에 둬 검은 띠를 막습니다.

### 5. 스토어에 올릴 수 있는 상태가 아닙니다

플레이어 설정이 전부 기본값입니다.

| 항목 | 현재 | 필요 |
|---|---|---|
| companyName | DefaultCompany | 실제 명의 |
| applicationIdentifier | 비어 있음 | com.xxx.bbong 형식 확정 |
| bundleVersion / versionCode | 1.0 / 1 | 버전 정책 수립 |
| AndroidTargetSdkVersion | 0(자동) | Play 요구 API 레벨 명시 |
| 아이콘 · 스플래시 | 없음 | 제작 |

패키지 ID는 한 번 올리면 못 바꾸니 상표 검토(`considerations.md` R5)와 같이 정하는 게 좋습니다.

**◐ 부분 해결(2026-08-13)** — `CliBuild.ApplyMobileSettings`가 빌드 시점에 명의(Yogoloper)·
패키지 ID(com.yogoloper.bbong)·타깃 SDK(자동)·ARM64/IL2CPP를 강제합니다(-versionCode /
-appVersion 인자 지원). 남은 것: 아이콘·스플래시 제작, 버전 정책, 상표 검토 확정.

### 6. 서버가 재시작을 못 버팁니다

방 상태가 전부 인메모리라 `fly deploy` 한 번에 진행 중인 게임이 전멸합니다. 지금은 `--ha=false`로
머신 1대에 고정해 쓰고 있어서 수평 확장도 불가능합니다. 웹 시연 단계에서는 감수할 만했지만, 실제
유저가 붙으면 배포할 때마다 사고가 납니다. 방 상태를 Redis 등으로 빼거나, 최소한 배포 전 신규
매칭을 막고 진행 중인 판이 끝나기를 기다리는 드레인 절차가 필요합니다.

### 7. 법무 검토를 아직 안 했습니다

`considerations.md` R1이 여전히 최대 변수입니다. GRAC가 BBONG을 웹보드게임으로 분류하면 월 결제
한도, 1회 베팅 한도, 일일 손실 한도, 자동 진행 제한이 붙고 판돈 시스템을 다시 설계해야 할 수도
있습니다. 이건 코드보다 앞서 확인해야 하는 사안이라 지금부터 별도 트랙으로 진행하는 게 맞습니다.
개인정보처리방침과 이용약관도 스토어 등록 필수 서류인데 아직 없습니다.

## 단계별 계획

법무(T)는 나머지와 병렬로 갑니다. 결과가 M6 수익화 설계를 좌우하기 때문에 가장 먼저 착수합니다.

### M3 — 모바일 기본기

앱으로서 최소한 성립하게 만드는 단계입니다. 여기까지 해야 실기기에 올려볼 수 있습니다.

1. ~~토큰 영속 저장 + 자동 로그인~~ ✅ (위 1번)
2. ~~만료 시 재인증~~ ✅ 최소 해법 (위 2번, 리프레시 토큰은 백로그)
3. ~~Android 뒤로가기 처리~~ ✅ (위 3번)
4. ~~세이프에어리어 대응~~ ✅ (위 4번)
5. 앱 일시정지/복귀 처리 — 복귀 시 끊김 감지(`AppHost.OnApplicationPause` → `NotifyIfDropped`)까지는
   됨. 백그라운드 소켓 수명·재접속 UX는 실기기에서 검증 필요
6. 실기기 빌드 후 첫 플레이테스트 — 터치 정확도, 프레임, 발열, 해상도별 레이아웃
   (에뮬레이터 2대 대전·튜토리얼 검증은 완료, 실기기는 미실시)

덧붙여 8-13~20 사이에 UI 정리도 끝났습니다: 메뉴 전 화면 색 토큰 통일(`UiTheme.cs`),
설정 오버레이, 프로필 전적/기록, 튜토리얼 전면 개편(교습 박스·42px 2줄·이전 되감기·
자연뽕 바가지 플레이어블 레슨), 카드 모션 60fps 안정화.

### M4 — 스토어 등록 준비

1. 패키지 ID·앱 이름·버전 정책 확정 (상표 검토와 함께)
2. 아이콘, 스플래시, 스토어 스크린샷, 피처 그래픽 제작

5. iOS는 Apple Developer Program($99/년) 필요 — 시점 판단

### M5 — 운영 안정성

1. 방 상태 외부화 또는 무중단 배포 절차 (위 6번)
2. 미정산 매치 타임아웃 정리 잡 (M2에서 남은 항목)
3. 서버 모니터링·알림 — 에러율, 방 수, 정산 실패
4. 크래시 리포팅 도입
5. 계정 삭제 요청 처리 경로 (스토어 정책 필수)

### M6 — 수익화와 경제 (법무 결과 확정 후)

1. IAP 연동 — `com.unity.purchasing` 패키지는 이미 들어와 있고 미사용 상태
2. 광고 SDK 실연동 — 현재 상점의 광고 보상은 서버 로직만 있고 실제 광고는 없음
3. 포인트 밸런스 재조정 — faucet/sink 균형 (`considerations.md` R3)
4. 담합 탐지 (R2) — 동일 IP·반복 매칭 패턴

### M7 — 출시

내부 테스트 → 클로즈드 테스트 → 오픈 테스트 → 프로덕션 순으로 올립니다. Google Play는 신규 개인
개발자 계정에 클로즈드 테스트 요건(일정 인원·기간)이 붙으므로 일정을 여유 있게 잡아야 합니다.

### T — 법무 (병렬, 지금 착수)

2. 분류 결과에 따른 판돈 시스템 대응안 마련
3. 상표 출원 검토 (R5)
4. 개인정보처리방침 (PIPA), 미성년자 결제 정책 (R4)

## 판단이 필요한 것들

- **안드로이드 먼저인지 양대 스토어 동시인지** — iOS는 연 $99에 심사가 더 까다롭습니다.
- **게스트 유지 여부** — 계정 영속을 붙여도 기기 분실·교체는 소셜 로그인이 있어야 복구됩니다.
  게스트를 계속 허용하되 소셜 연동을 강하게 유도하는 쪽을 권합니다.
- **판돈을 출시 버전에 넣을지** — 법무 결과에 따라 1차 출시는 판돈 없이(연습·친구방만) 내고,
  분류 확정 후 업데이트로 붙이는 선택지도 있습니다. 리스크를 가장 크게 줄이는 방법입니다.
- **서버 비용 구조** — 현재 fly 단일 머신. 동시 접속 규모 예측에 따라 리전·스펙 재검토가 필요합니다.
